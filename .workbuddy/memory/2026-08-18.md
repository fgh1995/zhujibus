## 修复：语音包配置获取时序竞争（race condition）

**问题**：用户反馈"配置加载失败，但抓包没切 URL"。根因是**时序竞争**——`VoicePackManager` 构造时立即 `initAsync()` 拉取语音包配置，此时 `configAccelUrl` 还是空串（`setConfigAccelUrl` 要等 `loadRemoteConfig` 完成才被 `applyRemoteConfig` 调用）。且 `initAsync` 的 `configFetching` 原子锁 + 单线程 executor 会导致推送后的重拉被吞掉，加速源（降级链第2级）形同虚设。

**修复方案**（按用户要求：先让 loadRemoteConfig 加载完，再去获取语音包配置）：
- `VoicePackManager`：
  - 构造器**不再**自动 `initAsync()`，改为等加速源就绪。
  - 新增 `volatile boolean accelReady`（加速源就绪标记）；`initAsync` 开头 `if (!accelReady) return;`。
  - 新增 `volatile boolean needRefetch`（防重入期间有拉取请求被吞时置位，结束后补拉一次）。
  - `initAsync` 的 `configFetching` 为 true 时不再直接 return，而是 `needRefetch=true`，本次结束后用 `doFetchConfigSafe()` 补拉。
  - `setConfigAccelUrl` 置 `accelReady=true` 并触发 `initAsync()`。
  - 新增 `unlockConfigFetch()` 兜底方法：loadRemoteConfig 失败时也解锁配置拉取，避免功能永久瘫痪。
- `MainActivity.loadRemoteConfig`：失败路径（http 非2xx / 解析失败 / IOException）调用 `VoicePackManager.getInstance(...).unlockConfigFetch()` 兜底解锁。

**用户偏好**：要求 AI 不要帮忙编译（"我自己编译"），只改代码即可。

## 修复2：首页/详情页主动拉取 cn_to_en（去除 configLoaded 永久拦截）

用户反馈"首页根本没有去拉 cn_to_en"、"参考 BusLineDetailActivity 的拉取方法"。

**根因**：`initAsync` 里的 `if (configLoaded.get()) return;` 永久拦截——一旦本地缓存解析成功使 `configLoaded=true`，后续 `initAsync` 永不拉取远程 cn_to_en；首页 `refreshVoicepackStatus` 重试也只读状态，没主动触发拉取。

**修复**（3 个文件）：
- `VoicePackManager.initAsync()`：**移除 `if (configLoaded.get()) return;` 拦截**，改为每次调用都拉取远程 cn_to_en（仍受 `accelReady` 门控 + `configFetching/needRefetch` 防重入）。
- 新增 `ensureConfigLoading()`：公开入口，直接 `initAsync()`（即使本地有缓存也拉远程最新）。
- `doFetchConfigSafe()` 补拉时去掉 `if (!configLoaded.get())` 条件。
- `MainActivity.refreshVoicepackStatus`：配置未就绪重试时调用 `vpm.ensureConfigLoading()`；重试次数 5→8。
- `BusLineDetailActivity.checkLineVoicepackStatus`：配置未就绪重试时调用 `vpm.ensureConfigLoading()`。

## 修复3：彻底放弃 accelReady 门控，恢复无条件拉取

**问题**：用户反馈"首页还是没有发出任何请求，随后就报失败了"。

**根因**：上一版引入的 `volatile boolean accelReady` 门控是祸根。`initAsync` 开头 `if (!accelReady) return;` 导致：
- 首页 `refreshVoicepackStatus` 每 2 秒重试（8 次=16秒）期间，`ensureConfigLoading → initAsync` 全部被 `!accelReady` 挡掉，一个请求都发不出。
- `accelReady` 要等 `loadRemoteConfig`（走 `github.360967.xyz` 慢速代理，可能挂起/超时 10s+）完成后才置 true，首页 16 秒内等不到就报"加载失败"。
- 语音包配置拉取**被动依赖一个慢速/可能挂起的代理**，这是设计缺陷。

**新方案**（放弃"先 loadRemoteConfig 再拉取"的阻塞式门控，改为"立即拉取 + 加速源就绪后强制重拉"）：
- `VoicePackManager` 构造器恢复 `initAsync()` —— 首页一启动就发请求拉 cn_to_en，不依赖 loadRemoteConfig 时序。
- `initAsync()` **删除 `if (!accelReady) return;`** 门控，改为无条件拉取（`configFetching/needRefetch` 防重入仍保留）。
- `setConfigAccelUrl()`：加速源变更（changed=true）时**强制用新加速源重拉**（即使 configLoaded 已 true，也走 executor 再 fetchConfig 一次）；未变更则走 `initAsync()`。
- `ensureConfigLoading()`：`configLoaded=true` 时直接 return（避免 UI 重试过度拉取），否则 `initAsync()`。
- `unlockConfigFetch()`：简化为 `initAsync()`（无阻塞，兜底）。
- **删除 `accelReady` 字段**。
- MainActivity / BusLineDetailActivity 调用不变（`ensureConfigLoading`/`unlockConfigFetch` 签名未变）。

**关键设计取舍**：用户最初要求"先 loadRemoteConfig 再获取语音包配置"，但该要求通过阻塞式门控实现，导致首页完全发不出请求。改为"立即拉取 + 切源重拉"后：既保证首页有请求，又能在 loadRemoteConfig 完成后用加速源重拉，降级链第 2 级仍能生效。**这是更稳健的方案，替代了门控方案。**

## 修复4：原始地址一直连接不切源（切源机制根治）

**问题**：用户反馈"原始地址一直在连接，然后一直不切源"。根因：
1. `new OkHttpClient()` 未配置超时（默认 connect/read 均 10s），`raw.githubusercontent.com`（大陆被墙）挂起时每源要白等很久，4 源串行最坏卡 40s+，观感是"一直连接不切源"。
2. 每次下载都从源0（被墙的原始地址）开始，前置源不可用时每次都被撞一次。

**修复**（`VoicePackManager.java`，仅此 1 文件）：
- **短超时**：`http` 改为 `new OkHttpClient.Builder().connectTimeout(5s).readTimeout(8s).writeTimeout(8s)`，任一源连接/响应超时快速失败立即切下一源。新增 `import java.util.concurrent.TimeUnit;`。
- **源记忆（preferredSource）**：新增 `volatile int preferredSource` 记录最近一次成功源序号。重构 `executeWithFallback` 为循环遍历：从 `preferredSource` 开始环绕遍历 4 源，命中成功源即记录并返回；`buildSourceUrl(idx)` 根据序号拼 URL（0=原始 raw / 1=configAccelUrl+originalUrl / 2=HARDCODED_FALLBACK+originalUrl / 3=GITEE_BASE_URL+filename）。
- `setConfigAccelUrl` 加速源变更时重置 `preferredSource=0`，让降级链从新配置源重新评估。

**效果**：被墙的原始地址 5s 内超时切源；某源（如 Gitee）成功一次后，后续请求优先直接走该源，不再重复撞前置不可用源。

## 修复5：配置实际返回了但 UI 显示"加载失败"（事件监听机制）

**问题**：用户反馈"返回配置了但显示加载失败"。根因：`fetchConfig` 内 `executeWithFallback` 串行走 4 源，即使 Gitee 成功也要先等前 3 源超时（5+8+8≈21s），远超 UI 固定重试窗口（首页 8 次×2s=16s，详情页 5 次×2s=10s）。**配置后台实际下载成功并 `configLoaded=true`，但 UI 重试窗口已耗尽显示"失败"，且不再刷新**（只靠 onResume 才重刷）。

**修复**（3 文件，为 VoicePackManager 增加"配置加载完成事件监听"，UI 收到事件主动刷新）：
- `VoicePackManager.java`：
  - 新增 `List<OnConfigLoadedListener> configListeners` + `interface OnConfigLoadedListener { void onConfigLoaded(); }`。
  - `addConfigLoadedListener(l)`：注册；若 configLoaded 已 true 则经 executor 立即回调一次。
  - `removeConfigLoadedListener(l)`：反注册。
  - `notifyConfigLoaded()`：快照遍历通知（synchronized 拷贝），`safeNotify` 捕获异常防崩。
  - `fetchConfig()` 末尾 `configLoaded.set(...)` 后，若为 true 则 `notifyConfigLoaded()`。
- `MainActivity.java`：
  - 新增字段 `voicepackConfigListener`；`refreshVoicepackStatus` 的 `!isConfigLoaded()` 分支调用 `ensureVoicepackConfigListener(vpm)`；configLoaded 分支调用 `unregisterVoicepackConfigListener(vpm)`。
  - `ensureVoicepackConfigListener`：幂等注册，回调 runOnUiThread 里 `voicepackStatusRetryCount=0; refreshVoicepackStatus()`（跳过固定重试窗口，立即统计）。
  - `onDestroy` 反注册防泄漏。
- `BusLineDetailActivity.java`：同样新增字段 + `checkLineVoicepackStatus` 的 `stat==null` 分支注册、`stat!=null` 分支反注册、`ensure/unregisterVoicepackConfigListener`、`onDestroy` 反注册。回调里 `voicepackRetryCount=0; checkLineVoicepackStatus()`。

**关键点**：监听器是"一次性"——UI 在 configLoaded 为 true 后即反注册，`setConfigAccelUrl` 重拉触发的 notify 不会重复刷新（因 UI 已反注册）。回调在 executor 线程，UI 需自行 runOnUiThread。

**遗留**：4 源串行首拉仍可能慢（源0/1/2超时后才到源3），监听机制保证"最终成功即刷新"，但首屏显示"加载中/失败"的等待时间仍取决于源切换耗时。

## 修复6：拉取触发与回调统一收敛到 VoicePackManager（消除首页/详情页各自为政）

**用户诉求**："VoicePackManager 类统一拉取触发和处理回调，而不是首页和详情页各自为政。" 即把降级链源遍历、重试计数、轮询、监听注册/反注册全部从 UI 抽走，统一由 VoicePackManager 内置状态机管理。

**重构（3 文件）**：
- `VoicePackManager.java`：
  - 新增 `enum ConfigState { LOADING, READY, FAILED }`。`LOADING`=源遍历中或重试等待中（UI 绝不判失败）；`READY`=配置就绪；`FAILED`=所有源遍历完且重试耗尽。
  - 新增 `ConfigStateListener` 接口（`onConfigStateChanged(ConfigState)`）+ `addConfigStateListener`/`removeConfigStateListener`。注册后立即回调当前状态一次（防漏通知），之后每次状态变更广播。
  - **内置重试状态机**：`startFetchCycle()` 为唯一触发入口（防重入 CAS + needRefetch 补拉）；`runFetchAndResolveState()` 拉完后调 `resolveConfigState()`：成功→`configLoaded=true`→READY（重置计数）；失败且 `configRetryCount<CONFIG_MAX_RETRY(8)`→自增、置 LOADING、用 `ScheduledExecutorService scheduler.schedule(2s)` 延迟重拉；耗尽→FAILED。
  - 新增 `ScheduledExecutorService scheduler`（延迟重试用）。
  - `setConfigAccelUrl` 变更时：重置 `preferredSource=0`、`configRetryCount=0`、置 LOADING、`startFetchCycle()` 强制用新加速源重拉。
  - `ensureConfigLoading()`：FAILED 态被调用时重置计数并置 LOADING 重新来过（用户手动重试入口）；READY 则跳过。
  - **移除旧 API**：`OnConfigLoadedListener`、`addConfigLoadedListener`、`removeConfigLoadedListener`、`notifyConfigLoaded`、`initAsync`、`doFetchConfigSafe`（全部由新状态机替代）。`fetchConfig()` 末尾不再 notify，状态解析统一走 `resolveConfigState`。
  - 保留 `isConfigLoaded()`/`isConfigFetching()`/`getConfigState()`/`ensureConfigLoading()` 供 UI 直接查用。
- `MainActivity.java`：
  - 删除 `voicepackStatusRetryCount` 字段；`voicepackConfigListener` 类型改为 `ConfigStateListener`。
  - `refreshVoicepackStatus()` 简化为：注册统一监听（幂等）+ `vpm.ensureConfigLoading()`，不再自建轮询/重试循环。
  - `ensureVoicepackConfigListener()`：注册一个 switch(state) 回调——LOADING→"加载中..."；READY→反注册+`renderVoicepackReadyStats`（原统计逻辑抽成独立方法）；FAILED→"加载失败"。
  - `onDestroy` 改用 `removeConfigStateListener` 反注册。
- `BusLineDetailActivity.java`：
  - 删除 `voicepackRetryCount` 字段；`voicepackConfigListener` 类型改为 `ConfigStateListener`。
  - `checkLineVoicepackStatus()` 简化为：收集站名 + 注册统一监听 + `vpm.ensureConfigLoading()`，删除原 `handler.postDelayed` 轮询。
  - `ensureVoicepackConfigListener()`：同 MainActivity 的 switch(state) 回调；READY→反注册+`renderLineVoicepackReady`（原统计逻辑抽成独立方法）。
  - `onDestroy` 改用 `removeConfigStateListener`。

**关键点**：重试次数统一为 8（详情页原 5 次也改为 8，达成"统一"）；回调在线程池/scheduler 线程，UI 回调内需 runOnUiThread；`addConfigStateListener` 立即回调当前状态，配合 `ensureConfigLoading`（READY 跳过）无重复拉取；FAILED 后 UI 重新进入（onResume/点重试）会重置计数重新拉取。

**效果**：首页与详情页不再各自维护 retryCount、轮询 Handler、监听生命周期——全部由 VoicePackManager 状态机统一管理，UI 只做"状态→文案"的映射。满足了"源遍历完成前不判失败、成功即时刷新、重试耗尽才判失败"。

## 修复7：下载语音包认准"当前正常拉配置的通道"（不再逐个源试）

**用户诉求**："下载语音包时，选择当前正常拉取配置文件的通道，而不是失败以后每个源都去尝试下载。"

**改动**（`VoicePackManager.java` 仅 1 文件，`executeWithFallback`）：
- 新增首通道捷径：`configLoaded.get()==true` 时（配置已就绪，`preferredSource` 即最近一次成功拉取 cn_to_en.json 的源序号），下载**直接只认该通道做单次尝试**，不再从 preferredSource 起环绕遍历全部 4 源。
- 该通道此刻也失败（临时抖动/源掉线）时，才回退走完整降级链兜底（仍从 preferredSource 环绕遍历），保证不会因捷径而丢失可用源。
- `configLoaded==false`（配置未就绪）时无可信通道记忆，行为不变：从 preferredSource 环绕遍历全部源。

**关键前提**：`preferredSource` 在 `executeWithFallback` 成功时 `preferredSource=idx` 写入；配置拉取（`fetchConfig` 也走 `executeWithFallback(CONFIG_FILENAME)`）成功后必已设为真实成功源。故配置就绪后，下载认准该通道必然可用，单次尝试即可命中，省去逐源尝试的等待与流量。

**边界**：配置从本地缓存解析成功（`configLoaded=true`）但远程拉取从未成功时，`preferredSource` 仍为 0（原始地址可能不可用）。此时首通道尝试失败即自动回退完整降级链，逻辑健壮，不漏可用源。

## 修复8：状态码 404 不视为失败（不降级）

**用户诉求**："状态码如果是 404 则不视为失败（降级）"。

**改动**（`VoicePackManager.java` 仅 1 文件）：将 `executeWithFallback` 的源尝试逻辑抽成独立方法 `trySource(idx, url, filename)`，明确区分两类失败：
- **404（终结性失败，不降级）**：服务器明确返回"文件不存在"。因各降级源（raw / githubAddSpeed / github.360967.xyz / Gitee）都是**同一份内容的镜像**，文件在一个源 404，其他源也必然 404，继续降级只会白白等待。故直接返回该 404 Response 停止遍历，交由调用方按 `isSuccessful()==false` 判定失败。
- **网络级失败/超时/5xx（源本身问题，才降级）**：`close()` 后返回 null，继续尝试下一源。

**`trySource` 返回约定**：成功 Response（2xx）/ 404 Response（终结）/ null（源不可用，降级下一源）。

**调用方兼容性**（无需改动）：`downloadFile` 和 `fetchConfig` 都用 `resp==null || !resp.isSuccessful()`（或 `resp!=null && isSuccessful()`）判定，404 Response 会走失败分支且被 `try-with-resources` 正确关闭，无泄漏。
