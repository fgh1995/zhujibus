## 修复：公交线路名含字母（108A/105L/Y1A路/9路B）的拆解与预制语音包合成

**问题**：站点/线路播报中，含字母的线路名识别拆解有问题——`108A`/`105L`/`Y1A路` 因 `Integer.parseInt` 失败整条走 TTS；`9路B` 数字用预制数字音频、字母后缀却走 TTS（半 TTS 半预制）。用户已在 `res/raw/` 新增 `cn_a.wav`~`cn_z.wav`、`en_a.wav`~`en_z.wav` 共 52 个单字母预制音频，但此前无任何代码引用。

**改动**（仅 `app/src/main/java/org/zjfgh/zhujibus/TTSUtils.java`）：
- 新增资源数组 `CN_LETTER_RES`(a-z→R.raw.cn_a..cn_z)、`EN_LETTER_RES`(a-z→R.raw.en_a..en_z)。
- 新增解析辅助：
  - `tokenizeLineName(name)`：按**原始字符顺序**拆为 token 序列——连续数字合并为 NUMBER、单字母为 LETTER、"路"为 ROUTE；遇中文等不可拆解字符返回 null → 整条 TTS（保留旧行为）。
  - `cnLetterRes`/`enLetterRes`/`addCnNumber`(≤100整读/>100逐字"幺"读)/`addEnNumber`(≤99整读/>100逐字)。
- 重写 `addCnLineNumber` / `addEnLineNumber`：严格按 token 原始顺序拼预制音频。
  - **中文**："路"出现在它本来的位置（例 `9路A` → 九+路+A，而非九+A+路）。
  - **英文**：若含"路"，先播 `en_route` 前置，再按原始顺序播字母/数字（英文习惯 "route" 放最前：例 `9路A` → route+nine+A；`Y1A路` → route+Y+one+A）。无"路"则无 route（如 108A）。

**拆解结果示例**（中文 / 英文）：
- `108A` → 一零八 + A（无路）/ one zero eight + A
- `105L` → 一零伍 + L（无路）/ one zero five + L

- `Y1A路` → Y + 一 + A + 路 / route + Y + one + A

**验证点**：`R.raw.cn_num_yao`、`cn_route`、`en_route`、`CN_NUM_RES[0..100]`、`EN_NUM_RES[0..99]` 均存在；`PlaybackItem(int)` 与 `PlaybackItem(String,Type)` 构造器存在。用户自行编译。

## 修复：TTS 与预制混播时 TTS 经常"速度变快"

**现象**：TTS + 预制语音包合并播报时，TTS 段经常比正常语速快（预制不变）。用户补充关键线索：**TTS 不在首段也会变快、且每条 TTS 段时好时坏**（如"开往+TTS小商品市场""to+TTS小商品市场"各段独立地偶尔变快/正常）——说明不是"首段"问题，而是**逐段、随系统负载而变化的偶发**。

**真正的根因**（`TTSUtils.java` `synthesizeTtsToWav`）：`tts.synthesizeToFile()` 是**异步**写文件，原代码用**固定 500ms `postDelayed` 盲等**再读文件。合成耗时随系统负载/引擎状态波动，常 >500ms → 读到**"半截文件"**：WAV 头或数据不完整，`parseWav` 解析出**错误采样率**（甚至触发 `<44` 字节回退假设 16000Hz），随后重采样（16000→22050 上采样或头声明 22050 而实际更慢）使该段**变快/变调**。哪条 TTS 段恰好在负载高时合成，哪条就变快——完美解释"逐段偶发、与是否首段无关"。

**双重修复**：
1. `synthesizeTtsToWav` 改为**精确等待合成完成**：注册 `utteranceId → CountDownLatch`，在全局 `UtteranceProgressListener.onDone/onError` 中 `countDown()`，`latch.await(8s)` 超时保护。文件完整后再 `readWavFile`，彻底消除半截文件。
2. 顺带（互补、仍必要）：合并重采样循环 `for (i = 1 → i = 0)`，保证**所有**段落（含首段）统一重采样到 22050；预制本就 22050 走 no-op。

**验证**：`python wave` 实测预制 raw WAV 均为 rate=22050 ch=1 width=16；外部无 `setSpeechRate` 调用（默认 1.0f）。新逻辑无 `postDelayed`/盲等，依赖 `onDone` 闩。

**改动点**：新增 `pendingSynthLatches`(ConcurrentHashMap)、`import Map/ConcurrentHashMap/TimeUnit`；全局 listener 增加闩释放；`synthesizeTtsToWav` 重写（nanotime 唯一 uttId、8s 超时、finally 清理+删临时文件）。未编译（用户自编译）。

## 修复：resampleOnly 重采样越界崩溃 (ArrayIndexOutOfBoundsException)

**崩溃栈**：`resampleOnly(TTSUtils.java:944)` ← `resampleAudio` ← `buildAndPlayMergedAudio`，抛 `length=43018; index=43019`。

**根因**：`resampleOnly` 末尾插值逻辑无条件读取 `srcIdx + 1` 这个相邻采样点（line 944 旧代码）。当重采样游标 `srcIdx` 落到**最后一个采样点**（`sourceSamples - 1`）时，line 937-940 已把其 `frac` 强制置 0（因为无法再向下插值），但旧代码仍去读 `pcmData[(srcIdx+1)*bytesPerSample+1]` —— 即 `pcmData[sourceSamples*bytesPerSample]`，**正好越界**。崩溃参数印证：`length=43018 → sourceSamples=21509`，越界 index `43019=(21508+1)*2+1`，`srcIdx=21508=sourceSamples-1`（被 clamp 末尾却又读下一位）。

**修复**：仅在 `frac > 0`（确实需要插值）时才读取 `sample2` 并做插值；`frac == 0` 时插值结果即 `sample1`，无需访问越界的下一位。16-bit 与 8-bit 分支同样处理。

**旁证**：`convertStereoToMono` 不读 `srcIdx+1`，故无此问题。修复后末端采样点安全。
